# Haiguitang Protocol v2

海龟汤语义合同的工程协议(5 大类)。**本文件是 v2 协议文字版的单一事实
来源** —— 代码里的常量在 `story/haiguitang_protocol.py`, 不要在
README / Issue / 其它模块复制本协议全文。

状态: **Active**。keyword2 正式生成路径已写 v2(代码注入
`protocol_version`)。

与 v1 的关系: v2 **延续** v1 的全部结构合同(completion 2~4 /
public_text 安全门 / established 判定 / victory ownership /
no-hidden-leakage), **唯一**的破坏性变化是主题分类轴: 11 类收敛成
5 大类。历史 v1(`haiguitang/protocol/v1.md`)**冻结保留**, v1 存量题
继续按 v1 校验, 绝不隐式升级。

---

## 1. Scope

同 v1 §1: canonical 数据合同 / 胜利表达 / 隐藏与展示边界 / 难度与主题
枚举 / 新旧数据兼容边界。不定义提示调度、题池补货、UI 呈现、生成
prompt —— 那些由各自模块拥有。

## 2. Version

    protocol_version: str, 非空枚举

    ""              legacy/current production schema(v2 之前的所有题)
    haiguitang-v1   历史协议(11 类), 只存在于存量题
    haiguitang-v2   本协议(5 大类), 新生成题一律写它

代码常量(`story/haiguitang_protocol.py`):

    PROTOCOL_V1               = "haiguitang-v1"   # 冻结
    PROTOCOL_V2               = "haiguitang-v2"   # 当前
    HAIGUITANG_PROTOCOL_VERSION = PROTOCOL_V2
    SUPPORTED_PROTOCOL_VERSIONS = ("", PROTOCOL_V1, PROTOCOL_V2)

**fail closed**: 任何其它非空值一律被 validator 拒绝 —— 绝不"不认识
就当 legacy"。`HAIGUITANG_PROTOCOL_VERSION` 从本协议起表达"当前正式
协议"; **表达"历史 v1"必须显式用 `PROTOCOL_V1`**, 不得再用"当前版本
常量"兼指两者。

四个版本字段严格区分, 不得合并(同 v1 §2):

| 字段 | 含义 | v2 当前值 |
|---|---|---|
| `spec_version` | JSON/archive **数据结构**版本 | 5 |
| `protocol_version` | 这道题的**语义合同**版本 | `""` / `haiguitang-v1` / `haiguitang-v2` |
| `quality_policy_version` | 项目**准入质量政策**版本 | `quality-v13` |
| `prompt_version` | 生成 **Prompt** 版本 | `haiguitang-generation-v2` |

`spec_version=5 + protocol_version=""` 仍然合法 —— 那是"新程序写出的
legacy/current 题"。

## 5. Categories —— 5 大类(本协议唯一破坏性变化)

canonical 主题枚举, 精确 **5 类**(代码常量 `V2_CATEGORIES`):

    logic, suspense, horror, emotion, brainstorm

### 5.1 语义: 体验轴, 不是元素清单

五大类回答一个问题: **观众玩这道题时, 主要获得的是哪种体验。**
不是简单看故事里出现了什么元素。

    logic       逻辑      主要乐趣来自因果 / 时间 / 身份 / 条件 / 顺序 /
                          空间 / 规则推导。即使有犯罪或反转元素,
                          只要核心 payoff 是"推出来了", primary 就是它。
    suspense    悬疑      主要乐趣来自调查 / 犯罪谜团 / 隐藏事件 /
                          谁做了什么 / 动机 / 线索重建 / 真相追查。
                          旧 v1 的 crime 大多数靠近这里, 但**不能机械
                          按关键词映射**。
    horror      恐怖      主要体验是恐惧 / 诡异 / 压迫 / 危险 / 不安 /
                          恐怖真相。只是出现死亡**不**自动等于恐怖。
    emotion     情感      主要 payoff 来自家庭 / 亲情 / 爱与失去 / 悲剧 /
                          温情 / 人际关系 / 情绪重构。旧 v1 的
                          family / tragedy / warm 靠近这里。
    brainstorm  脑洞      主要乐趣来自非常规设定 / 意义翻转 / 用途翻转 /
                          荒诞 / 科幻想象 / 喜剧型误导 /
                          "原来还能这样"。旧 v1 的 twist / comedy /
                          sci_fi 靠近这里。

**不要增加第六类, 不要自行改名。**

### 5.2 观察判定

- 新题必须由 Contract/Audit **直接按五类观察最终成品**; 不能先判
  旧 11 类再机械映射。
- `primary_category`(observed 主类别)+ `categories`(1~3 条)的
  结构合同同 v1 §13: 无重复、全在五类里、primary ∈ categories。
- `content_style` / `style_tags` / `mechanism_family` / `domain` /
  `emotion_mode` 保持原职责, 不顶替 categories(同 v1 §13)。
- 坏数据不做静默修复(同 v1 §13): `["brainstorm","brainstorm"]` 原样
  保留, 由 validator 报 duplicate; 非法值不自动回退。

### 5.3 版本分派(validator / schema / prompt 三处同源)

类别枚举**必须**按 spec 自报的 protocol_version 查表
(`categories_for`):

    ""          -> 无枚举(协议层零附加约束)
    v1          -> 11 类(V1_CATEGORIES, 冻结)
    v2          -> 5 类(V2_CATEGORIES)

同一份 spec 在**同一条链上**被读取的三处必须用**同一个版本**的枚举:

1. `validate_protocol`(story/haiguitang_protocol.py)
2. Reviewer 的 tool schema(`check_tool` -> `_v1_check_tool(cats_enum=...)`)
3. Reviewer 的 system prompt(audit 文字: v1 题 -> `audit-v1.md`,
   v2 题 -> `audit-v2.md`)

**prompt 与 schema 不允许异版本配对** —— "v2 五类 prompt + v1 11 类
schema"(或反过来)都会让模型按一套标准填、代码按另一套标准拒。

## 6. Legacy v1 展示映射(presentation-only)

直播 UI 最终只应出现五大类。历史 v1 题的**展示**走确定性兼容映射
(代码常量 `LEGACY_V1_DISPLAY_CATEGORY`):

    logic                     -> logic
    suspense / crime          -> suspense
    horror                    -> horror
    family / tragedy / warm   -> emotion
    twist / brainstorm /
    comedy / sci_fi           -> brainstorm

硬边界:

- 它**只**是 `legacy v1 -> 直播五类展示` 的兼容层, **不是**把旧题重新
  审了一遍; 不写回 PuzzleSpec、不改盘、不做在线 LLM 重分类。
- 直播热路径(pop_next / submit_riddle / snapshot)**零** LLM / 零网络
  调用 —— 展示映射是纯查表。
- 新 v2 题**绝不**经过这个 mapping(它自身已是五类)。
- 唯一入口是 `public_puzzle_meta(spec)`(§7)。

## 7. public_puzzle_meta —— presentation-safe 合同

一道题对外展示的元数据**只有一个来源**:
`haiguitang_protocol.public_puzzle_meta(spec)`。返回形状:

    {
      "difficulty": "medium",
      "difficulty_label": "中等",
      "primary_category": "suspense",
      "primary_category_label": "悬疑",
      "categories": ["suspense", "brainstorm"],
      "category_labels": ["悬疑", "脑洞"],
    }

合同(全部确定性, 零 LLM, 零 I/O):

1. **按版本分派**: v2 直接用五类字段; v1 走 §6 映射; 其余一律空。
2. **legacy("")/unknown 整体空 dict** —— 难度也不下发。前端安静
   隐藏, 绝不显示"未知 · 未分类", 也**绝不只下发难度**(半套元数据
   等于暗示"这题有合法分类数据")。
3. **分类整体自洽才下发**: `primary_category` 非法/为空、或映射后
   不在 categories 的映射结果里时, 分类四把键整体不出现 —— **绝不**
   把某个 secondary "晋升"成新的 primary。从坏数据猜分类等于代码替
   审核员重选 primary, 那是编造分类事实。
4. **难度独立判**: v1/v2 下 difficulty ∈ {easy,medium,hard} 才下发,
   非法不下发; 缺难度时分类照常下发(两条独立轴)。
5. **primary 恒排第一**; 映射后去重, 保持首次出现顺序。
6. **绝不出现** `requested_category`(生成意图不是分类事实)、fact id、
   hidden truth(answer / canonical text / completion ids)。
7. 中文 label 的单一来源在本模块: `CATEGORY_LABELS`(五类)/
   `DIFFICULTY_LABELS`(三档)。前端不维护第二份 enum→中文映射。

## 8. Generation Pipeline Contract(v2)

    GenerationBrief(requested_category, difficulty)
        → Truth → Surface → Contract → Audit
        → validate_spec(共同规则) + validate_protocol(版本专属)

- `GenerationBrief` 是"**当前新生成请求**"的合同: 非空
  requested_category **只接受五类**(历史 v1 的请求枚举是另一回事,
  不混入)。非法值在任何 LLM 调用之前 fail closed。
- `protocol_version` 由**代码**在生成收尾注入(`haiguitang-v2`),
  模型 tool schema 里没有它, 模型不输出、不改写它。
- `prompt_version` = `haiguitang-generation-v2`(generation Pack 总
  版本; Contract/Audit stage 文件为 v2)。Judging Pack 独立版本,
  不受本协议牵动。
- Audit **看不到** requested_category(blind classification 保持)。
- v2 spec 仍必须过当前 live safety policy(quality 系统拥有)。

## 9. Compatibility

- 历史数据不迁移不改写(同 v1 §16): v1 题缺五类字段也不猜不补,
  v1 的 11 类 categories 原样保留。
- `spec_version` 维持 5 —— v2 没有增删 PuzzleSpec 的持久化字段,
  只收窄了枚举语义。
- Pool / refill / 投票 / Demand Refill 不属于本协议(后续 Phase)。
