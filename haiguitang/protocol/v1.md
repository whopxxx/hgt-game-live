# Haiguitang Protocol v1

海龟汤语义合同的工程协议。**本文件是协议文字版的单一事实来源** ——
代码里的常量在 `story/haiguitang_protocol.py`, 不要在 README / Issue /
其它模块复制本协议全文。

状态: **Phase A(冻结 schema 与 validator)**。生产生成器尚未产 v1
(见 §16 / §17)。

---

## 1. Scope

本协议定义"一道海龟汤题"在 runtime 的 canonical 数据合同:

- 一道题由哪些部分组成(`PuzzleSpec`);
- 胜利条件如何表达、由谁判定;
- 哪些字段是隐藏真相、哪些可以展示给观众;
- 难度与主题的固定枚举;
- 新旧数据的兼容边界。

本协议**不**定义: 提示调度、题池补货、UI 呈现、生成 prompt ——
那些由各自模块与后续 Phase 拥有。

## 2. Version

    protocol_version: str, 非空枚举

    ""              legacy/current production schema(本协议之前的所有题)
    haiguitang-v1   本协议

代码常量: `HAIGUITANG_PROTOCOL_VERSION = "haiguitang-v1"`,
受支持集合 `SUPPORTED_PROTOCOL_VERSIONS = ("", "haiguitang-v1")`。

**fail closed**: 任何其它非空值(如 `haiguitang-v999` / `banana` /
`v2`)一律被 validator 拒绝 —— 绝不"不认识就当 legacy", 否则未来新协议
数据会被旧程序静默按 legacy 语义播出。

四个版本字段严格区分, 不得合并:

| 字段 | 含义 | 当前值 |
|---|---|---|
| `spec_version` | JSON/archive **数据结构**版本 | 5 |
| `protocol_version` | 这道题的**语义合同**版本 | `""` / `haiguitang-v1` |
| `quality_policy_version` | 项目**准入质量政策**版本 | `quality-v13` |
| `prompt_version` | 生成 **Prompt** 版本 | `riddle-v9` 等 |

`spec_version=5 + protocol_version=""` 完全合法 —— 那是"新程序写出的
legacy/current 题"。

## 3. Canonical PuzzleSpec

`story.puzzle.PuzzleSpec` 就是本协议的 canonical case object。
**没有**第二个平行 case 类 —— 协议讨论里的 "PuzzleCase" 一律由
`PuzzleSpec` 承担, 避免两份事实源。

v1 新增字段(全部 `PuzzleSpec` 顶层, 宽容读, 缺失 = 未声明):

    protocol_version: str  = ""     # §2
    difficulty:        str  = ""     # §12
    primary_category:  str  = ""     # §13
    categories:        list = []     # §13
    requested_category:str  = ""     # §14

`PuzzleFact` 新增:

    public_text: str = ""           # §8

Phase A **不做隐式升级**(§16): 读入时缺失字段保持未知, 不猜、不补、
不从别的字段映射。

## 4. Puzzle / Answer / Core Answer

三个文本字段职责不同, 不得混淆:

| 字段 | 是什么 | 给谁看 |
|---|---|---|
| `puzzle` | 汤面 —— 观众看到的谜题 | 观众 |
| `answer` | 完整隐藏真相(允许背景与故事性细节) | 仅主持人/Judge/verifier |
| `core_answer` | 一句话核心解释, 直接回答汤面的主要异常 | 揭晓时原样念给观众 |

`answer` **不是**通关合同; `core_answer` **不是** public fact
(它只在揭晓后出现)。

## 5. Facts

`facts[]` 是这道题世界的 **canonical 事实空间** —— 主持人整局判断
"是/不是/无关"的依据。每条 `PuzzleFact`:

    id          稳定标识
    text        canonical truth(Judge / verifier 判定真相用)
    kind        core / support / exclusion
    visibility  public / hidden
    hintable    提示可否围绕它引导
    public_text 已建立后的安全展示摘要(§8)

## 6. Completion Contract

`completion_fact_ids` 是**最小胜利合同**: 房间必须真正建立的核心事实
集合。判定: `completion_fact_ids ⊆ established_fact_ids`。

条数合同按协议版本分档:

    legacy/current (protocol_version="")   1 ~ 2 条
    haiguitang-v1                          2 ~ 4 条

- 2~4 是**允许区间**, 不是"鼓励写 4 条"; 确定性校验不得产生
  "最好写满"的激励。
- 每条 completion fact 仍必须是: id 存在、`kind=core`、
  `visibility=hidden`, 不得重复; v1 额外要求**非空 `public_text`**。
- completion 条数与 discovery beats 数量**无关**(§10)。

## 7. Established vs Touched

    touched      = 观众问过这个方向(不确认真假)
    established  = 该事实已公开确认为真, 进房间共识

`touched` **永不**推进通关, **永不**进入公开展示。established 只能由
真人 QA 经 `verifier -> Engine` 链写入(§15)。

## 8. Public Fact Contract

`PuzzleFact.public_text` = 该事实被真人**正式建立之后**可以展示给直播
观众的安全摘要。

安全边界(硬合同):

1. `public_text` **不是** canonical truth 的别名, 不允许"反正
   `text` 也能显示"——validator 对 v1 completion fact 缺
   `public_text` 判**整份 spec 不合法**, 而不是运行时补救;
2. 唯一出口是 `PuzzleSpec.public_established_completion_facts(
   established_fact_ids)`:
   - 输入只有 `established_fact_ids`(参数名即合同, **不接受** touched);
   - 输出 = `completion_fact_ids ∩ established_fact_ids`,
     `text` 只取 `public_text`;
   - `public_text` 为空(legacy/未填)→ **跳过该条**, 绝不 fallback;
   - 顺序 = `completion_fact_ids` 的合同顺序(不是 set / facts[] 顺序),
     UI 的"已确认 2 / 4"需要稳定顺序;
3. 公开内容最终仍受当前项目 live safety policy 约束(由 quality 系统
   拥有, 本协议不重复定义)。

## 9. Solve Atoms

`solve_atoms` 是谜底的**分析拆分**(提示 / 解释 / 复盘用), **不是**
通关合同。atom 通过 `fact_ids` 引用 fact; "说中 atom"与"探明 fact"
是两件事。每个 completion fact 应至少被某条 atom 引用(公平性抓手;
缺失属可修的 metadata wiring, 语义沿用现有 quality 系统)。

## 10. Discovery Beats

`discovery_beats` = 正常游戏中观众**逐层发现**的节奏(2~4 条),
**没有任何胜负权** —— beat 全覆盖 / 数量 / hint / 任何自动机制都不得
建立 established 或触发 solved。

completion 与 beats **不存在一一对应**: "4 beats 2 facts" 与
"3 beats 3 facts" 都合法。禁止把两条数据当同一张表写。

## 11. Fair Clues

`fair_clues` = 汤面原文里**已经真实存在**、回看能指向谜底的具体事实。
`quote` 必须逐字出现在谜面里(允许全角/半角/引号/空白轻度归一),
由 `quote_in_puzzle` 确定性验证, 不做模糊语义判断。

## 12. Difficulty

`difficulty` 固定枚举, 代码常量 `DIFFICULTIES`:

    easy / medium / hard

- v1: 空、`normal`、`困难` 等一律非法; legacy 的 `""` 合法(未知)。
- **completion 条数 ≠ 难度**(2 facts ≠ easy, 4 facts ≠ hard)。
  两者是独立轴, 禁止互相推断; 将来用真实直播数据重新校准难度。

## 13. Categories

canonical 主题枚举, 精确 **11 类**(代码常量 `CATEGORIES`, 不要改拼写,
不要新增 mystery / romance / dark / emotional / thriller):

    logic, suspense, horror, twist, brainstorm,
    family, crime, tragedy, warm, comedy, sci_fi

`primary_category`(audited observed 主类别)+ `categories`(1~3 条):

    1 <= len(categories) <= 3
    无重复, 全部属于 11 类
    primary_category ∈ categories

`primary_category` 的语义**就是** observed/audited primary —— **没有**
第二个 `observed_category` 字段, 不得新增, 否则"谁是真的"无法回答。

`content_style` / `style_tags` / `mechanism_family` / `domain` /
`emotion_mode` 全部保留原职责, **不得**改名或顶替 categories ——
例如 `mechanism_family=identity_misread` + `primary_category=crime` +
`categories=[crime, suspense, twist]` 完全合法。

坏数据不做静默修复: `from_dict` 对 `["crime","crime"]` 原样保留,
由 validator 报 duplicate; 非法 category 不自动回退成 logic。

## 14. Requested vs Primary

`requested_category` 是 **provenance**(这次生成任务当初要求什么),
不是这题"是什么"; `""` 合法(自由生成 / curated import / 无定向需求),
非空必须是 11 类之一。

**requested != primary 是合法状态**:

    {"requested_category": "sci_fi",
     "primary_category": "suspense",
     "categories": ["suspense", "sci_fi"]}

validator **必须放行** —— 它表示"生成了一份合法的悬疑+科幻题, 但没
完成'补一题主科幻'的业务需求"。"需求是否 fulfilled"属 Phase D 的
Demand Refill, 不是 schema validity。

`requested_category` **不得**进入 Judge / 答题 / 通关链 —— 判汤底时
知道"本来要求生成科幻"会形成 classification bias。

未来库存消费语义(Phase D 才实现, 现在冻结定义防争论):

    普通候选: theme ∈ categories 即满足该主题
    选择优先级: primary == requested > secondary includes requested
    Demand Refill fulfilled: primary_category == requested_category

## 15. Victory Ownership

**LLM 没有最终决定 SOLVED 的权限。** 判题链:

    viewer message
        ↓
    Judge interpretation
        (touched_fact_ids / proposed_established_fact_ids)
        ↓
    completion verifier(复核 + verdict「是」门)
        ↓
    Engine 合并 approved established facts
        ↓
    completion_fact_ids ⊆ established_fact_ids
        ↓
    SOLVED

以下**都不**具有胜负权: `solve_atoms`、`discovery_beats`、
`fair_clues`、hint、AI player、touched facts、Judge 的一句"你猜中了"。
Engine 现行集合覆盖算法**不变**, 天然支持 2/3/4 条合同。

## 16. Legacy Compatibility

- 旧题缺 `protocol_version` / `difficulty` / `primary_category` /
  `categories` / `requested_category` / `PuzzleFact.public_text`:
  读取时保持未知(`""` / `[]`), **不做任何隐式升级** —— 不猜
  difficulty、不把 `content_style` 映射成 categories、不用
  `text` 补 `public_text`、不把 1 条 completion 拆成 2 条、
  不按 answer 调 LLM 补 metadata。Phase A 是 schema upgrade,
  不是 migration。
- legacy 的 completion 行为(1~2 条)不变: 既有校验、错误文案、
  测试继续成立; `MAX_COMPLETION_FACTS = 2` 保持原值, 只对 legacy 生效。
- `spec_version` 4 → 5: 新 archive 写 5; 旧 version 4 与缺
  `spec_version` 的 archive 照常可读。

## 17. Generation Pipeline Contract

Phase A 冻结未来管线的形状, **本阶段不接线**:

    GenerationBrief(requested_category, difficulty)
        → Truth → Surface → Contract → Audit
        → validate_spec(共同规则) + validate_protocol(版本专属)

- `GenerationBrief` 是生成**意图**值对象(frozen dataclass,
  `story/haiguitang_protocol.py`), `""` = 不指定; 非空必须属枚举;
  确定性 `validate()` 拒非法值。**不接进** gen_spec / keyword_seed /
  prefetch / Director(Phase B/D)。
- current quality-v13 池**不被本协议 quarantine**: 现有题的
  `protocol_version=""`, live eligibility 不变。
- 当前生产 prompt 继续生成 legacy schema(`protocol_version=""`)——
  什么让 LLM 按合同产 v1, 属 Phase B。
- 最终 `PuzzleSpec` 仍必须通过当前项目的 live safety policy
  (由现有 quality 系统拥有)。

## 18. Security / No Hidden Fact Leakage

汇总本协议的安全硬门:

1. `public_text` 为空 → 展示 helper 跳过该条; canonical `fact.text`
   **永不**作为前端 fallback;
2. 未 established 的事实不进任何展示(§8);
3. `touched` 不得被当成 established 使用(§7);
4. `answer` / `core_answer` / canonical `text` 只进主持人 /
   Judge / verifier 侧, 不进观众可见快照;
5. v1 completion fact 缺 `public_text` = 整份 spec 不合法(fail closed),
   不做运行时兜底。
