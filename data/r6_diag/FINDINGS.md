# R6 诊断：`livestream_safe` 的漏判是**抖动**，不是判据覆盖不到

**Issue** #8 的后续 · **PR** #9 blocker `5754904316`
**不改代码、不改 Prompt、不改 policy。** 只诊断。

---

## 先纠正一个前提（你提的，对的）

**重跑不可能还原"当时 Reviewer 返回了什么"。** 原始 `quality_checks`
从来没落盘，那个值**已经丢了**。

重跑只能回答：**当前 `check-v10` 对同一份冻结产物会怎么判**。
所以下面每一条结论都必须读成"当前判据在这道题上的行为"，
而**不是**"当时那一次判了什么"。

冻结的 spec 里 `puzzle` / `answer` / `facts` / `atoms` / `clues` 都在盘上，
所以重审的是**同一份产物**，没有重生成 Story / Surface。

---

## 结果

`tools/r6_review_probe.py`，各跑 3 次，完整九项 `quality_checks` 存
`probe.json`。

| 行 | lane | keywords | 3 次 `livestream_safe` |
|---|---|---|---|
| 1 | black | 列车上 / 威胁 | **False / True / False** |
| 3 | black | 网络 / 假发 | **False / True / None**（第 3 次审稿技术失败） |

### 行 3（我自己判定"应当 false"的那道）

`False / True / 技术失败`。**不是 3 次都 false。** 这直接推翻了我上一轮
的假设 —— 我当时说"判据+模型能识别，原始那次是漏判"，**太早了**。

### 行 1

`False / True / False`。同样**抖**。

---

## 结论：两种事故**同时**存在

1. **抖动 / 漏判（主因）。** 同一份冻结产物，同一份 `check-v10`，
   三次里能给出不同的 `livestream_safe`。单次判定不可靠 —— 这是
   **可靠性**问题，不是判据措辞问题。
2. **判据边界确实存在。** 行 1 两次 false 一次 true，说明它在边界上；
   行 3 也是 2:1。**但** `False` 出现过，说明判据**够得着**这两道题 ——
   不是"判据覆盖不到"。

所以修法方向是 **可靠化**（多次判定取多数 / 保守取否），
**不是**继续加判据措辞。后者按 R4-R3 的纪律本来也不该做。

⚠️ **必须说明的局限**：n=3、2 道题。这个样本**不足以**给出错误率，
只能说"单次判定在这两道上是抖的"。要谈错误率需要更大的样本。

---

## 顺带：门本身是好的（排除你说的第 2 种情况）

`test_r4r3_livestream_safe_false_rejects_free_gen` 绿：

```
ok  **审稿确实跑到了**
ok  **拒因点名 livestream_safe**
ok  **整稿被要求重出**
ok  **改回 true 后不再因 livestream_safe 被拒**
```

所以「Reviewer 判 false 但代码侧门漏了」**不成立**。
`livestream_safe=false` 会进 `quality_checks 未全过(...)`，整稿被拒。

## 观察到的另一个信号（不在本 issue 范围，但值得记）

重审时 `single_trick`（curated 侧的字段）在行 1/3 反复出现 `False`。
它**不在自由生成的九项契约里**，所以不影响判定 —— 但说明 Reviewer
在两套清单之间会混着填。这是 `check-v10` 契约措辞的一个小噪声，
**本轮不改**，只记录。

## 建议的下一步（等你定，不在 PR #9 里）

**`livestream_safe` 单次判定不可靠** → 它是硬门，漏一次就有题上播。

选项：

- **A. 安全项多数票**：只对 `livestream_safe` 这一项跑 2~3 次，
  任一 false 即 false（保守取否）。成本：每道题 +1~2 次审稿调用。
- **B. 安全项独立复核**：审稿通过后，再用一次**只判安全**的调用
  复核。比 A 便宜（不重跑整份九项），且关注点单一。
- **C. 先不做**：只在观测上把落盘做好（已做），攒够样本再决定。

我倾向 **B** —— 它是"判据不变、只加一次针对性复核"，最符合
"不继续堆规则"的纪律；而且它天然是 fail-closed 的（复核说不安全就拒）。

但这是**新的行为改动**，会改 accept/reject，**要 bump policy**，
所以**不该混进 PR #9**。
